# PS Vita Port Audit: Freelancer-Decomp

## 1. Проверка утверждений документации

### Все ли обязательные модули одиночной игры имеют исходники?
**Да.** Согласно `docs/ru/re/dll_inventory.md` и исходному коду, все движковые DLL (DACOM, DALib, EngBase, x86math, Common и т.д.), а также модули одиночной игры (`freelancer.exe`, `Content.dll`, `rpclocal.dll`, `Server.dll`) имеют исходники на C++ в директории `src/`.

### Какие оригинальные бинарники действительно загружаются?
Из оригинальных (retail) бинарников загружаются только сторонние компоненты:
- `EBUEula.dll` — диалоговое окно лицензионного соглашения (загружается через `LoadLibraryA` в `src/freelancer/Client/main.cpp`).
- `gundll.dll` — клиент GUN для мультиплеера (список серверов).
В самой игре для одиночного режима другие retail DLL не загружаются (пути переопределяются в `bin/DACOM.INI` на `.\`).

### Можно ли исключить EBUEula, GUN, RemoteClient, RemoteServer и FLServer из отдельной single-player сборки, сохранив Server и rpclocal?
**Да.**
- `EBUEula.dll` легко отключается в `freelancer/Client/main.cpp` (удалением вызова `LoadLibraryA` и пропуском показа EULA).
- `gundll.dll` (GUN) не используется в SP.
- `RemoteClient.dll` и `RemoteServer.dll` реализуют сетевой транспорт через DirectPlay для мультиплеера и могут быть полностью исключены.
- `FLServer.exe` — это отдельное MFC-приложение (выделенный сервер), не требуемое для SP.
- В SP-режиме клиент `freelancer.exe` подключается к игровой логике напрямую через `rpclocal.dll`, которая выступает прокси к `Server.dll`. Обе эти DLL полностью портированы и достаточны для работы локального сервера в одиночной игре.

## 2. Подтверждённые препятствия для VitaSDK (с путями и символами)

### x86math и Inline Assembly (x87, naked functions)
- `src/x86math/x86math.cpp`: Множество функций, таких как `FFastDot::FastDotZZZ` и др. (строки 271-560), объявлены как `__declspec(naked)`. Это MSVC-специфичное расширение, не поддерживаемое в таком виде для ARM (и архитектура команд совершенно иная).
- `src/include/x87_trig.h`, `src/x86math/x86math.cpp`, `src/Thorn/SplineMath.h`, `src/Thorn/ThornScene.cpp`: Активно используются блоки `__asm` для математики на FPU x87 (например, `fld`, `fstp`, вычисление синусов/косинусов). На ARM (Vita) сопроцессор другой, поэтому требуется переписать этот код на стандартные функции `<cmath>` или интринсики ARM.
- `src/zlib/vendor/crc32.c`: Присутствуют `__asm__ volatile` инструкции (например, `crc32x`), некоторые из которых специфичны для aarch64, что может вызвать ошибки компиляции на 32-битном ARM процессоре PS Vita.

### DACOM: DllMain, LoadLibrary, GetProcAddress
- `src/dacom/dacom.cpp` (строка 1317) и `src/freelancer/Client/main.cpp`: Активно используется `LoadLibraryA` для загрузки модулей (в т.ч. `rpclocal.dll` и `Server.dll`), а также `GetProcAddress` для получения `GetClientInterface` и фабрик компонентов (в `IServerImpl.cpp`).
- На PS Vita нет WinAPI-загрузчика DLL. Возможные пути:
  1. Использовать `sceKernelLoadModule` для `.suprx` модулей.
  2. **Статическая регистрация компонентов:** Заменить динамическую загрузку на статический реестр, где движок будет вызывать функции инициализации модулей напрямую, а компоненты будут регистрироваться глобальными конструкторами (без `DllMain`).

### WinAPI, COM, DirectInput, DirectSound, DirectPlay
- **Окна и ввод:** `freelancer.exe` (`freelancer/Client/main.cpp`) содержит `WinMain`, цикл обработки сообщений Windows (`HWND`, `WndProc`). Ввод использует DirectInput. Требуется рерайт `main.cpp` на кроссплатформенный фреймворк (например, SDL2) или нативные API Vita (`sceCtrl`).
- **Звук:** `src/SoundManager` и `src/SoundStreamer` используют DirectSound, EAX и ACM, инициализируемые через COM (`CoCreateInstance`). Потребуется создание нового бэкенда аудио (на базе `sceAudio` или кроссплатформенных либ, например SoLoud).
- **Сеть:** DirectPlay используется в `DALib` и сетевых модулях. Для SP это можно вырезать или заменить.
- **SEH:** Структурированная обработка исключений (SEH, `__try`/`__except`) иногда встречается в Windows-коде и не поддерживается стандартным C++ GCC.

### RP8 (DirectX 8)
- `src/RP8/`: Рендерер жестко привязан к Direct3D 8. Включает заголовочные файлы DX8 SDK (`d3d8.h`, типы в `Rp9D3d8Types.h`).
- Граница между интерфейсом движка и D3D проходит по виртуальным интерфейсам (`IRenderer`, `IRenderPipeline`). Для Vita потребуется полностью новый бэкенд (на базе VitaGL или GXM), реализующий эти интерфейсы.

### Packing, Alignment, Pointer-to-Integer
- В коде массово применяется `#pragma pack(push, 1)` и `#pragma pack(push, 4)` (например, `src/include/render/rendcomp.h`, `src/freelancer/Client/cli_asteroid.h`, `src/include/common_server_types.h`, а также физика `IVP`).
  - *Объяснение важности проверок layout:* Структуры должны точно совпадать по байтам с сетевыми пакетами или бинарными файлами (Bini, THN).
  - Процессор ARMv7 на Vita генерирует Data Abort exception при невыровненном доступе к памяти. Необходимо убедиться, что компилятор GCC (VitaSDK) понимает эти директивы упаковки или заменить их на `__attribute__((packed))`, чтобы компилятор генерировал безопасные инструкции побайтового чтения.
- Преобразования указателей: 32-битная архитектура Vita совпадает с Win32 (`sizeof(void*) == 4`), но следует проверять преобразования указателей в числа, чтобы избежать проблем строгого алиасинга.

## 3. Какие модули можно перенести без изменения игровой логики

Следующие модули в основном содержат игровую и физическую логику, не зависящую от платформенных API (при условии замены `__asm`):
- `Common.dll` (физика IVP, qhull, математика объектов, протокол)
- `Content.dll` (миссии, AI)
- `EngBase.dll`
- `Server.dll` (игровая логика сервера)
- `rpclocal.dll` (локальный RPC транспорт)
- `dacom.dll` (после адаптации механизма загрузки)
- `Thorn.dll` (скрипты сцен, Lua)
- `flmaterials.dll`, `alchemy.dll`, `Shading.dll`, `RendComp.dll` (логика отрисовки и батчинга на высоком уровне абстракции).

## 4. Какие модули требуют нового backend

- **RP8** -> Требует нового нативного рендерера (VitaGL / GXM).
- **SoundManager** / **SoundStreamer** -> Требуют нового аудио-бэкенда (sceAudio).
- **freelancer.exe (Client / WinMain)** -> Замена цикла Win32 окон и DirectInput на SDL2 / Vita API.
- **DALib** -> Исключение DirectPlay; базовая инициализация приложения.
- **ReadFile** -> Адаптация `SearchPathA` и путей файловой системы для работы с `ux0:`.
- **movie.dll** -> Отвечает за проигрывание видео (ASF/WMV). Потребуется нативный плеер `sceAvPlayer` или заглушка.

## 5. Упрощённые или ещё не восстановленные функции

Согласно `docs/ru/re/server.md` и документации:
- Многие функции `pub::SpaceObj` / `pub::Player` в `IServer` упрощены по сравнению с retail: создание объектов без полного пайплайна лодаута, упрощенные AI-формации, физические импульсы через сообщения вместо прямых вызов IVP. (Помечены как `simplified` в трекере).
- Из 162 типов пакетов `rpclocal` раскладка полезной нагрузки восстановлена не для всех; для невосстановленных в нагрузке передаются сырые DWORD аргументов.
- Механизмы чата и вывод краш-отчетов в `FLServer` / клиентском фильтре также не являются побайтовыми копиями оригинала.
Эти упрощения достаточны для функционирования порта на Windows и могут быть перенесены на Vita "как есть".

## 6. Минимальный граф зависимостей одиночной игры

Для запуска базового SP без видео, звука и сети потребуется следующий набор абстракций:
1. `freelancer.exe` (точка входа, адаптированный главный цикл).
2. `DALib` (старт движка).
3. `dacom` (загрузчик компонентов, INI парсер).
4. `ReadFile` (файловая система, настроенная на `ux0:`).
5. `x86math` (математика, очищенная от asm).
6. `Common` (в т.ч. физика IVP).
7. Заглушечный или минимальный бэкенд рендерера (заменяющий RP8).
8. Модули: `EngBase`, `Thorn`, `Shading`, `RendComp`, `alchemy`, `flmaterials`.
9. `rpclocal` и `Server` (SP игровая сессия).
10. `Content` (миссии и AI).

Все сетевые DLL (`RemoteServer`, `RemoteClient`), `FLServer.exe`, `movie.dll`, EULA и `gundll` могут быть исключены из процесса сборки и загрузки.

## 7. Первый небольшой этап для VitaSDK

**Цель:** Добиться успешной компиляции базовой, независимой от рендера инфраструктуры под ARM/VitaSDK, сохранив работоспособность Windows-сборки.

**План действий:**
1. **Настройка системы сборки:** Создать `CMakeLists.txt` (или адаптировать скрипты) для сборки модулей `x86math`, `ReadFile`, `dacom` под инструмент VitaSDK (`arm-vita-eabi-gcc`).
2. **Переписывание x86math:**
   - Заменить `__declspec(naked)` функции в `src/x86math/x86math.cpp` на стандартный C++ код. Использовать `#ifdef __arm__` или `#ifndef _WIN32` для сохранения оригинальной Windows-логики, если это критично для производительности на ПК.
   - Устранить зависимость от `__asm` x87 в `src/include/x87_trig.h` и других местах, заменив на вызовы `<cmath>`.
3. **Адаптация файловой системы (ReadFile):**
   - Написать кроссплатформенные обертки для WinAPI-функций работы с путями (`SearchPathA`) с помощью `std::filesystem` или POSIX API.
4. **Адаптация DACOM:**
   - Скрыть вызовы `LoadLibraryA` и `GetProcAddress` за кроссплатформенными абстракциями (`#ifdef _WIN32` для Windows, а для Vita — подготовка почвы под статическую линковку или `sceKernelLoadModule`).
5. **Проверка выравнивания:**
   - Скомпилировать эти модули с флагами предупреждений для выравнивания (например `-Wcast-align`). Убедиться, что GCC VitaSDK понимает `#pragma pack(push, 1)`. При необходимости использовать кроссплатформенный макрос `PACKED_STRUCT`, раскрывающийся в `__attribute__((packed))` на GCC/Clang и `#pragma pack` на MSVC.
